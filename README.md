You have access to multiple repositories that together make up one application. Analyze all accessible repositories and help me understand the complete project so I can explain it confidently in a software engineering interview.

First, inspect the repository structure, README files, build files, configuration, source code, database scripts, CI/CD workflows, tests, and deployment files. Trace how the repositories communicate with each other.

Please produce the following:

1. Project overview
- What business problem does this application solve?
- Who are the primary users?
- What are the major capabilities of the platform?
- Avoid making unsupported assumptions. Clearly label anything inferred from the code.

2. Repository breakdown
For each repository, explain:
- Its purpose
- Main technologies and frameworks
- Important modules and folders
- Whether it is frontend, backend, data processing, authentication, infrastructure, or another service
- How it interacts with the other repositories

3. End-to-end architecture
Explain the complete data and request flow:
- Where data originates
- How it is processed or aggregated
- Where it is stored
- How backend APIs retrieve it
- How the frontend displays it
- Authentication and authorization flow
- CI/CD and deployment flow
- Logging, monitoring, testing, and error handling

Create a simple text-based architecture diagram.

4. Technical deep dive
Identify:
- Main REST APIs
- Important services, controllers, components, jobs, and database tables
- Batch-processing or aggregation workflows
- Database technologies
- Cloud services
- Security implementation
- Performance or scalability patterns
- Important design patterns
- External integrations

5. Interview-ready explanation
Write:
- A 30-second project summary
- A 60–90 second project explanation
- A detailed 3-minute explanation
- A non-technical explanation for a recruiter
- A technical explanation for a senior engineer

The explanation should naturally cover:
- Business problem
- Architecture
- Technology stack
- My likely responsibilities as a full-stack software engineer
- How features move from requirements through development, testing, deployment, and production support

6. My potential responsibilities
Based on the codebase, list realistic responsibilities I could discuss, such as:
- Developing frontend features
- Building or modifying REST APIs
- Updating database schemas
- Working with data-processing pipelines
- Writing unit tests
- Troubleshooting production issues
- Supporting releases and CI/CD

Do not claim that I personally completed something unless I confirm it. Separate verified project facts from possible responsibilities.

7. Interview questions
Generate at least 20 likely interview questions about this project, including:
- Architecture
- Scalability
- Database choices
- API design
- Security
- Data processing
- CI/CD
- Testing
- Production troubleshooting
- Individual contribution

For every question, provide a strong sample answer grounded in the repositories.

8. STAR story opportunities
Identify 5–8 situations in the codebase that could become STAR stories, such as:
- A difficult defect
- A data-quality problem
- A performance issue
- A failed deployment
- A cross-repository feature
- A production incident
- A release challenge

For each one, explain what additional information you need from me to create an accurate STAR response.

9. Evidence
For every important technical conclusion, reference the repository name and relevant file paths. Do not expose credentials, secrets, customer information, or proprietary data.

At the end, provide:
- A glossary of important project terms
- A list of areas I should study further
- Any contradictions or unclear architecture decisions you found
- Ten follow-up questions you need me to answer to personalize the interview explanation
